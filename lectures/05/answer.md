## 宿題

### 基礎

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を5から8に変更し、通常のベクトル検索で返す件数を増やした。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」。モデルは `gemini-3.5-flash-lite`、対象は第1〜3回の本講義資料・同じ検索DB、実行方法は `uv run python -m app.agent --trace` で固定した。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 変更前（`RAG_TOP_K=5`）：回答は「LoRAは元の重みを固定し、低ランクの差分を学習。QLoRAは元の重みを4bitに圧縮」と説明し、第2回・PDF p.51、52を引用。traceは `search_materials({'query': 'LoRA QLoRA 固定 学習'})` が1回。3.21秒、入力／出力 3,027／218 tokens、モデル応答2回、生成API推定費用 $0.001453。
  - 変更後（`RAG_TOP_K=8`）：同じ要点を説明し、第2回・PDF p.51、52を引用。traceは `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` が1回。3.05秒、入力／出力 4,442／195 tokens、モデル応答2回、生成API推定費用 $0.001820。
  - 検索語を固定した単独検索では、変更前の上位5件は p.52、p.51、p.60、p.61、p.47。変更後はこれらに p.54、p.58、p.23が追加された。回答の直接の根拠であるp.51・52は両方で取得できた。traceのツール返却表示は先頭部分のみなので、ページ一覧と本文は `uv run python -m app.retrieval 'LoRA QLoRA 固定 学習'` でも確認した。
- 改善した例と、残る失敗・制約：この質問では回答や引用根拠の改善は確認できなかった。上位5件で必要な根拠はそろっており、8件では関連の薄いページも増え、入力トークンと推定費用が増えた。各条件1回のみの実行なので、時間や回答の揺れは評価できていない。
- 気づき・疑問：検索件数を増やしても、既に十分な根拠を取得できている質問では回答の質が上がるとは限らず、追加文脈のコストが増える。質問の種類ごとに、必要な根拠の取りこぼしと追加ページのノイズを評価して `RAG_TOP_K` を決めたい。

### 実装

- 取り組んだレベル：実装
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/retrieval.py` で、検索上位ページの前後1ページを同じ資料内から追加するようにした。元の検索ヒットを先に保ち、追加ページには `match_type: adjacent` と根拠元のページIDを付ける。同じページが複数ヒットの隣接ページになる場合は1件に統合する。資料境界・重複を確認するテストも追加した。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は「LoRA・QLoRAでは何を学習し、どんなときにFine-Tuningを選ぶのですか？」。モデル `gemini-3.5-flash-lite`、第1〜3回の本講義資料、検索DB、`RAG_TOP_K=8` を固定し、変更前後とも `uv run python -m app.agent --trace` で実行した。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 変更前：通常検索は8ページ（p.51、52、58、23、60、47、46、61）。traceは `search_materials({'query': 'LoRA QLoRA 学習 Fine-Tuning 選ぶ'})` が1回。回答はLoRA/QLoRAの説明とFine-Tuningの判断基準を回答したが、検索結果にないp.57も引用していた。4.61秒、入力／出力 4,247／825 tokens、モデル応答2回、生成API推定費用 $0.003337。
  - 変更後：同じtraceのツール・引数・回数。検索結果は元の8ページに隣接9ページ（p.50、53、57、59、22、24、48、45、62）を追加した計17ページ。p.57のチェックリストやp.50の判断順、p.53の「振る舞いと知識」の説明が取得され、回答ではp.50・53・57を根拠として利用した。4.83秒、入力／出力 7,801／673 tokens、モデル応答2回、生成API推定費用 $0.004023（生成API費用。埋め込み・索引構築分は含まない）。
  - 不要情報の例：狭い質問「LoRA QLoRA 固定 学習」では、変更前の上位8ページに対し、変更後は隣接ページを含む18ページになった。追加されたp.22（学習データの時点）、p.24（事後学習の前後）、p.62（次回のエージェント）はLoRA/QLoRAの仕組みを答える根拠には不要だった。いずれの比較でも同じページIDの重複はなく、追加は同じ講義資料内に限られた。
  - traceのツール返却表示は先頭部分のみのため、全ページと補足表示は `uv run python -m app.retrieval` でも確認した。`uv run pytest -q tests/test_build_rag_index.py` は3件成功。
- 改善した例と、残る失敗・制約：変更前は未取得のp.57を回答が引用していたが、変更後はp.58の隣接ページとしてp.57を取得し、チェックリストの根拠が得られた。一方、取得ページ数が8から17に増えた例があり、入力tokens・推定費用も増えた。隣接ページが必ず質問に有用とは限らず、今回は各条件1回のため時間・回答の揺れは評価できていない。
- 気づき・疑問：ページ境界で分かれた根拠を補える一方、上位ページ数が多いと周辺情報も大量に増える。隣接ページの有用性を保ちつつ、重複排除だけでなく追加数や関連度を制御する方法も検討したい。
